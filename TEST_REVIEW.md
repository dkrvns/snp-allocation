# Проверка силы тестов

Исходный набор: 59 тестов на коммите `ee30d0b`. После дополнения: 88 тестов.
Существующие тесты и исходники приложения не изменены. Все проверки выполнены
в Docker с Python 3.14.

## Что было сильным

- `allocation_test.py::test_allocate_matches_step_by_step_reference` сравнивает
  оптимизированный алгоритм с пошаговым на 300 воспроизводимых наборах.
- `csv_cases_test.py::test_allocate_csv_case` использует фиксированные планы,
  а не ожидаемые значения, вычисленные проверяемым алгоритмом.
- Отдельно проверяются строгий приоритет, округление до перехода к младшему
  приоритету, остаток, партии, дубликаты ID и независимость от порядка строк.
- Негативные CSV-тесты проверяют конкретный тип ошибки и её объяснение;
  CLI-тесты подтверждают отсутствие частично напечатанного плана при ошибке.

## Какие пробелы закрыты

| Исходная проверка | Какую ошибку пропускала | Добавленное доказательство |
| --- | --- | --- |
| `allocation_test.py::test_allocate_matches_step_by_step_reference` | Только один приоритет, положительные данные, малые числа и кратность от 1 | Независимый перебор допустимых количеств на 1000 наборах с несколькими приоритетами и некорректными заявками; отдельные граничные сценарии |
| `allocation_test.py::test_allocate_large_volume_is_fast` | Неверный выбор заявки из-за замены точных долей на float: сумма отгрузок сохраняется | Фиксированный план на больших целых числах, где последние три единицы должны уйти B, A, B |
| `cli_test.py::test_main_prints_all_sample_cases_and_diagnostics` | Нули в колонке отгрузки, неверная колонка спроса, потерянные предупреждения | Проверка всех полей таблицы и отдельного предупреждения о неизвестном кейсе |
| `csv_io_test.py::test_load_cases_preserves_bom_blank_lines_and_quoted_values` | Подмена периода и источника; нет проверки нескольких кейсов | Все метаданные, перемешанные заголовки, дополнительные колонки, BOM заявок и привязка перемежающихся заявок к двум кейсам |
| Косвенная проверка diagnostics через CLI | Пропажу сообщений о нулевом спросе, кратности 0, эффективной партии и превышении спроса | Точные списки сообщений, все отрицательные поля, нулевой приоритет и обе стороны границы минимальной партии |
| Вызов `main()` из теста | Удалённый запуск модуля и поломанный установленный console script | Настоящие subprocess-запуски `python -m snp_allocation` и `snp-allocation` с проверкой результата |
| Негативные проверки CLI | Необработанный UnicodeDecodeError и дубликаты заявок на границе CLI | Код 2, сообщение в stderr, отсутствие traceback и частичного плана |

Новые сценарии находятся в `allocation_contract_test.py`, `csv_contract_test.py`,
`cli_contract_test.py` и `diagnostics_test.py` в каталоге `tests/`.
Ожидаемые планы заданы явно; случайный эталон не импортирует `Lot`, приватные
функции или результат `allocate()` для вычисления своего ответа.

## Эксперимент с намеренными ошибками

В отдельном контейнере последовательно внесены 32 изменения в копию исходников.
После каждого изменения запускался весь pytest с остановкой на первом падении;
между запусками исходники восстанавливались, bytecode-кеш удалялся.
Для каждого прогона был внешний таймаут 10 секунд.

- Исходный набор обнаружил 14 ошибок, пропустил 17; ещё одно изменение эквивалентно.
- Усиленный набор обнаружил все 31 проверяемую ошибку. Таймаутов и ошибок сбора нет.
- Эквивалентное изменение — удаление начальной сортировки входных заявок.
  Ничьи всё равно разрешаются по ID в очереди и при округлении; меняется только
  порядок ключей результирующего dict, который контракт не фиксирует.

Проверены подмена порядка приоритетов, допуск нулевого приоритета и отрицательных
ограничений, потеря проверки дубликатов, неверная трактовка кратности 0, потеря
минимальной партии и округления, границы бюджета, float вместо Fraction,
потеря CSV-проверок и BOM, неверные метаданные, потеря diagnostics, неверные
колонки CLI, потеря предупреждений, запуска модуля и обработки UnicodeError.

Это результат для перечисленных ошибок, а не полный mutation score проекта
и не доказательство отсутствия других дефектов.

## Оставшееся ограничение

`allocation_test.py::test_allocate_large_volume_is_fast` измеряет время после
возврата функции. Он обнаружит замедление, но не прервёт бесконечный цикл или
чрезмерно долгий расчёт. Для исправления нужно выполнять расчёт в отдельном
процессе с таймаутом. Тело существующего теста оставлено согласно `AGENTS.md`:
изменение его сценария требует отдельного разрешения пользователя.

Полный pytest, Ruff format/check и mypy проходят. Абсолютный порог скорости
также зависит от доступного контейнеру CPU.
