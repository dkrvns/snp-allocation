# 04. База данных, gateways и транзакции

Применяется при наличии БД. SQLAlchemy/PostgreSQL/Alembic — профиль для выбранного
стека, а не обязательная зависимость любого Python-проекта.

## ORM и gateway

- Используй термин Gateway для адаптера доступа к данным. Каждая сущность/агрегат
  имеет отдельную реализацию; не собирай все gateways в один файл.
- SQLAlchemy 2: `Mapped`, `mapped_column`, `select/insert/update/delete`,
  `AsyncSession.scalar/scalars/execute`. Не добавляй legacy `session.query`.
- Типы, nullable, ограничения длины и индексы указываются явно. Persistent-инварианты
  подтверждаются UNIQUE, FK и CHECK, где они применимы, а не только if перед записью.
- Общий Base использует naming convention для стабильных имён ограничений.
  Alembic должен видеть все модели через явную регистрацию импортов.
- ORM-модели, DB committer и DB rate limiter находятся в `infrastructure/db/`.
  DB session не является application DTO и не передаётся в presentation/domain.
- Gateway возвращает mapped DTO, без ORM-объекта и случайного lazy loading.
  Преобразование оформляется явным mapper. Пустой результат — тот же DTO с defaults.

```python
async def get_by_id(self, user_id: UUID) -> UserDTO:
    row = await self._session.scalar(
        select(UserModel).where(UserModel.id == user_id)
    )
    if row is None:
        return UserDTO()
    return self._to_dto(row)
```

`scalar()` при отсутствии строки может вернуть `None`. Чтение `row.id` в этом
случае вызывает ошибку, а не возвращает None. Проверка до mapper обязательна.
Операции записи должны также обрабатывать конфликт ограничений и отсутствие
ожидаемой записи согласно своему контракту.

## Владение транзакцией

- Несколько связанных изменений одного инварианта фиксируются одной транзакцией.
  В gateway нет самостоятельного commit; он выполняет свою операцию записи.
- Command/Handler владеет границей commit через узкий Committer/UnitOfWork.
  Его реализация вызывает реальный commit; ошибка не превращается в успех.
- DB session создаётся на запрос и закрывается в `finally`/async context manager;
  незавершённая транзакция откатывается. На ошибке записи нельзя оставлять
  частично изменённое состояние для следующего запроса.
- Если неверная попытка или отзыв должны сохраниться даже при отказе клиенту,
  это отдельное явно описанное решение: фиксируй нужное состояние до выбрасывания
  ожидаемой ошибки и проверь результат новой независимой session.
- Для гонок используй условные UPDATE/UPSERT, row locks или version checks.
  Определи единый порядок блокировок и применяй его во всех связанных операциях.
  Чтение, затем безусловная запись не защищают от конкуренции.
- При повторном locked read учитывай SQLAlchemy identity map:
  `populate_existing=True` нужен, если требуется перечитать уже загруженную модель.
- Сетевой HTTP/SMTP-запрос не должен удерживать DB-транзакцию и row lock.
  Durable-доставка проектируется с outbox; простой синхронный эффект имеет
  отдельно описанное поведение при частичном успехе и неизвестном результате.

## Соединения и производительность

- Engine/pool/sessionmaker создаются один раз на lifecycle приложения, AsyncSession —
  на запрос. Выбери один PostgreSQL-driver, например psycopg или asyncpg.
- Настрой pool size, overflow, pool timeout, connection timeout и deadline запроса.
  Значения выбираются по нагрузке; бесконечные ожидания не являются настройкой.
- DSN берётся из Config и собирается безопасно средствами библиотеки.
  Не конструируй SQL через f-string из пользовательских значений.
- Списки имеют ограничение размера/пагинацию. Индексы обосновывай реальными запросами;
  проверяй N+1 и планы для критичных выборок. Не индексируй всё на будущее.

## Миграции и хранение данных

- Изменение схемы требует новой Alembic revision. Генерация, просмотр diff,
  upgrade и проверка соответствия моделям выполняются на отдельной БД в Docker.
- Уже применённые миграции не переписывай. У новой миграции проверь downgrade
  и повторный upgrade. Если обратимость означает потерю данных, обозначь это
  явно и согласуй план; пустой downgrade не считается рабочим откатом.
- Data migration отделяется от изменения схемы. Тесты миграций используют свою
  схему/БД и очищают только её, никогда рабочие таблицы.
- `expires_at` означает правило срока действия, а не автоматическое удаление строки.
  Retention и физическая очистка — отдельная эксплуатационная политика.
- Для учебного проекта не добавляй Python cleanup scripts без требования.
  При необходимости рассматривай штатные возможности БД/планировщика/партиций;
  их наличие и настройку нужно проверить. TTL-функции нет «у любой БД по умолчанию».
- Не удаляй историю, необходимую для аудита, replay detection или восстановления,
  только потому, что отдельный технический credential уже использован.
