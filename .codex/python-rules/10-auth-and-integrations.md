# 10. Auth, почта и внешние эффекты

Применяется, когда проект содержит соответствующую техническую подсистему.
Конкретные TTL, число попыток и транспорт выбираются требованиями проекта;
настройки учебного сервиса не переносятся как универсальные константы.

## Размещение и зависимости

- Registration/login/refresh/logout и техническая смена credentials находятся
  в `infrastructure/auth/handlers/<area>/`, выпуск токенов — в её `tokens/`.
  В application не импортируется конкретный TokenIssuer из infrastructure.
- PasswordHasher, token codec/generator и другие реализации разделены на модули
  `infrastructure/security/`. SMTP/HTTP adapters и system clock имеют свои модули.
  DB rate limiter относится к `infrastructure/db`, не к общей папке gateways.
- Готовый auth-framework, например fastapi-users, не подключается без явного
  решения пользователя. Собственная orchestration не означает самостоятельную
  реализацию криптоалгоритмов: Argon2/JWT/TLS используют проверенные примитивы.
- Бизнес-доступ, владение, членство и предметные ограничения проверяются
  соответствующей application/domain операцией. Подпись JWT не доказывает право
  менять любой ресурс, а middleware identity не заменяет object-level authorization.

## Credentials, сессии и токены

- Пароль хранится только как проверенный password hash. Ограничивай длину входа
  и параллелизм дорогого хэширования. Не возвращай hash в API.
- JWT проверяет signature, разрешённый algorithm, issuer, audience, exp и тип;
  обязательные claims не считаются optional из-за успешного decode.
- Связывай principal, сохранённую сессию и существующего активного пользователя.
  Пустой DTO, неизвестная session и несовпадающий user_id дают отказ.
- Refresh secret хранится в БД как digest; при ротации старый помечается использованным,
  новый сохраняется и связывается с нужной сессией до успешного ответа.
- Политики replay, абсолютного/скользящего срока и отзыва документируются.
  Если replay отзывает сессию, commit этого отзыва не теряется из-за HTTP-ошибки.
- Logout и смена пароля должны отзывать ровно согласованный набор credentials.
  Обновление пароля и отзыв необходимых сессий атомарны. Locks берутся в едином порядке.
- Секреты не логируются и не выводятся в интерфейс. Client storage/cookie policy
  выбирается явно: cookie auth требует CSRF, CORS allowlist, Secure/HttpOnly/SameSite;
  bearer auth требует безопасной работы клиента с токенами. Не сохраняй credentials
  в постоянный browser storage по умолчанию без оценки угроз и решения проекта.
- При ротации refresh клиент объединяет параллельные запросы, если повтор
  трактуется сервером как replay. Флаг busy и поведение после ошибки проверяются отдельно.

## Подтверждение email и rate limit

- Код генерируется криптографически стойко и привязывается к назначению и адресу.
  Для короткого OTP используй keyed digest/HMAC, чтобы простой dump БД
  не позволял перебрать весь небольшой диапазон без серверного секрета.
- Сервер задаёт срок, число попыток, одноразовость и cooldown. Пересылка меняет
  предыдущий credential по выбранной политике; неправильные попытки сохраняются.
- Создание аккаунта и использование проверенного кода имеют общую транзакцию,
  если invariant требует отсутствия неподтверждённого пользователя. При ошибке
  создания данные и состояние кода полностью откатываются.
- По одному email счётчик и замена кода атомарны. Добавляй серверный per-client/IP
  и общий лимит по требованиям; несколько replicas используют общий источник состояния.
- UI отображает оставшееся время по deadline и учитывает Retry-After. После
  ошибки и сброса busy кнопка не включается раньше разрешённого срока.
- Сроки UI и сервера согласованы. Консервативный Retry-After допустим как
  документированный верхний предел; это не повод менять контракт ради старого теста.
  Изменение существующих assertions проходит обычное согласование.
- Перезагрузка страницы и отключение JavaScript не должны обходить серверный лимит.
  Один таймер кнопки не является защитой от сетевого DDoS.

## SMTP и сетевые adapters

- Host, port, sender, transport security и credentials берутся из отдельного Config.
  Не помещай рабочий SMTP-пароль в пример, тест, image или запрос пользователя.
- Для простого клиента допустима stdlib smtplib в ограниченном пуле потоков.
  Блокирующий вызов не выполняется в event loop. Настрой timeout операций,
  ограничение concurrency и общий бюджет ожидания; socket timeout не гарантирует
  дедлайн всей цепочки DNS/connect/TLS/auth/DATA.
- SSL/STARTTLS проверяют сертификат и hostname; credentials не передаются через
  plaintext. Локальный тестовый SMTP без credentials — отдельная явная dev-конфигурация.
- При подтверждённом принятии DATA не превращай сбой последующего QUIT в сигнал
  повторно отправить то же письмо. Отказ адаптера переводится в стабильную ошибку,
  исходный текст SMTP-ответа не попадает клиенту или в публичный traceback.
- HTTP-клиент переиспользуется на lifecycle приложения, имеет timeout/pool limits
  и закрывается при shutdown. Поддержка retry зависит от идемпотентности операции,
  а не только от кода ошибки сети.

## Состояние БД и доставка

При требовании durable-доставки используй outbox/очередь с отдельным worker и
политикой дедупликации. Для простого синхронного учебного сценария допустима
явно выбранная последовательность commit выдачи кода → SMTP → ответ; при ошибке
выданный код инвалидируется условно, чтобы не затереть более новую выдачу.
Сетевой вызов не держит DB lock. Учитывай crash и неизвестный исход; этот вариант
не даёт гарантии отправки после падения процесса между commit и SMTP.

В тестах используй отдельный Mailpit/аналог без пересылки во внешние ящики и
отдельные получатели. Проверяй реальное письмо, число отправок и rollback при сбое.
Локальный почтовый catcher не означает, что письмо доставлено в реальный внешний ящик.
