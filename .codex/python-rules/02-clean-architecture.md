# 02. Архитектура и границы ответственности

Применяется к дизайну сервиса и изменению зависимостей. Модели, контракты и
структура модулей уточняются в разделе 03; техническая auth-подсистема — в 10.

## Выбор сложности

- Сначала опиши операцию, её инварианты, вход, результат, ошибки и внешние эффекты.
  Затем выбирай структуру. Для CLI/скрипта достаточно функций и адаптеров;
  для простого сервиса — orchestration и gateways; rich domain нужен для
  существенных предметных правил, а не ради наличия папки `domain`.
- DDD, CQRS, event sourcing, outbox и saga не являются обязательным стеком.
  Применяй их, когда можно назвать решаемую проблему и проверяемый результат.
- Существующую архитектуру меняй в рамках задачи. Не превращай исправление
  endpoint в массовый перенос файлов и не добавляй абстракции на будущее.
- При нескольких bounded contexts зафиксируй их владение данными и контракты
  взаимодействия. Разные части системы могут иметь разную внутреннюю сложность.

## Направление зависимостей

```text
presentation -> application -> domain
infrastructure -> application / domain
ioc / main -> все слои для связывания
```

- `domain` содержит предметные инварианты и не знает про ORM, HTTP, DI или I/O.
- `application` содержит бизнес-команды, interactors, DTO и нужные им порты.
  Он не импортирует SQLAlchemy, FastAPI, инфраструктурные реализации и DI framework.
- `infrastructure` реализует доступ к БД, внешним API, криптографии, почте,
  системному времени и техническим подсистемам.
- `presentation` переводит входной транспорт в вызов операции и обратно.
  Для бизнес-сценария он вызывает application; для технического auth-сценария
  допустим вызов `infrastructure/auth/handlers`, как явно выбранной границы.
- `ioc.py` связывает порты с реализациями; `main.py` собирает приложение и lifecycle.
  Не используй composition root как место бизнес-правил.
- Запрет импорта из application в infrastructure действует и косвенно:
  compatibility modules, `__init__`-реэкспорты и переименованные aliases его не обходят.

## Command, Interactor, Handler

| Роль | Назначение | Типичное расположение |
| --- | --- | --- |
| Command | Меняет бизнес-состояние и фиксирует предметную операцию | `application/commands/<area>/` |
| Interactor | Чтение или одно атомарное прикладное действие без собственной бизнес-мутации | `application/interactors/<area>/` |
| Handler | Оркестрация технического сценария, например регистрации или обновления credentials | `infrastructure/<subsystem>/handlers/<area>/` |
| Gateway | Операции над БД или внешним источником по контракту | `infrastructure/gateways/` или адаптер подсистемы |

Для изменяющего бизнес-состояние сценария выбирай Command, даже если он атомарный.
Атомарность операции не равна одному SQL-запросу: проверка, запись и commit могут
составлять одну операцию. Не создавай универсальную папку/класс `use_cases`.
Interactors не должны незаметно изменять бизнес-состояние под видом чтения.

Аутентификация, регистрация credentials и выпуск токенов относятся к технической
подсистеме. Приглашения в организацию, платный доступ и правила владения ресурсом
могут быть бизнес-логикой: их размещение определяется смыслом, а не словом user.

## Предметная модель, если она нужна

- Entity имеет identity; value object задаёт проверенное значение и обычно immutable.
  Aggregate root отвечает за инварианты своего агрегата и скрывает внутренние изменения.
- Domain-объект не должен существовать в недопустимом состоянии. Пустой DTO чтения
  не является пустой domain entity; эти контракты не объединяются ради экономии класса.
- Правила цен, статусов, лимитов и переходов располагаются в domain, если это
  rich domain model. Application оркестрирует load → действие → save → commit.
- Не дроби одну необходимую атомарную операцию на несколько commit ради лозунга
  «одна таблица/агрегат за транзакцию». Граница определяется инвариантами.
- Между независимыми контекстами используй опубликованные DTO/события/API,
  а не чтение чужих таблиц и импорт внутренних domain-классов.
- Надёжная асинхронная доставка события требует durable outbox/очереди и идемпотентного
  обработчика. Вызов после commit сам по себе не даёт гарантии доставки.

## Упрощение и рефакторинг

Разделяй ответственность, когда файл смешивает роли или область начинает расти.
Не вводи BaseGateway, универсальный service layer и иерархии из одноимённых
обёрток без потребителя. Удаляй устаревшие пути импорта в рамках согласованной
миграции и обновляй импорты напрямую. Совместимость публичного API библиотеки
проектируется отдельно; она не служит оправданием случайным внутренним shims.
