# 06. Содержательные тесты и их изменение

Применяется к тестам, фикстурам и ревью покрытия. Цель — обнаружить нарушение
контракта, а не увеличить число тестов, mocks или процент coverage.

## Разрешение на изменения

- В существующих тестах и фикстурах можно обновлять импорты при рефакторинге.
  Изменение assertions, входных данных, mock-поведения, набора сценариев,
  параметризации, имён, удаление, skip/xfail и ослабление проверки требует
  явного разрешения пользователя. Не обходи запрет через helper или conftest.
- При ревью сначала назови каждый слабый тест: файл/функция, какую ошибку он
  пропускает и предлагаемая правка. Затем получи согласие и меняй согласованный
  объём, включая необходимые supporting fixtures. Уже выданное согласие действует;
  не спрашивай его снова перед каждой строкой и отправкой, если она тоже разрешена.
- Новые осмысленные тесты разрешены. Они не заменяют и не отключают молча старые.
- Массовые format/fix по тестам не применяй при запрете менять их тело. Импорты
  исправляются отдельно, нетронутые файлы проверяются в read-only режиме.
- При изменении контракта покажи расхождение и нужную правку теста. Не меняй
  поведение продукта только ради старого expected и не выдавай частичный прогон
  с исключённым падающим тестом за полный успешный набор.

## Что считать хорошей проверкой

- Для теста можно назвать конкретный дефект, при котором он упадёт.
  Формулируй сценарий через наблюдаемое поведение и инвариант.
- Arrange → act → assert. Ожидаемое значение не вычисляется той же проверяемой
  функцией. Сначала проверь статус/успех, затем обязательные данные и эффекты.
- Условие не должно быть истинным из-за пустой коллекции или отсутствующего
  вызова: перед отрицательной проверкой подтверди, что нужные записи/вызовы есть.
- Не допускай `pass`, `assert True`, tests-only wrappers и mocks, проверяющих
  только другой mock. Геттер DTO или пустой `__init__.py` не требуют отдельного теста.
  Проверка пустого DTO, возвращённого реальным gateway при отсутствии записи,
  содержательна: это установленный контракт чтения.
- Отказ проверяется вместе с отсутствием запрещённых изменений; успех записи —
  вместе с фактическим состоянием БД. Ошибка не должна скрывать частичное изменение.
- Граничные значения включают обе стороны границы, например до cooldown и точно
  на его окончании. Таймеры проверяются управляемыми часами, а не ожиданием TTL.
- Не пиши тест ради каждого обратимого малозначимого изменения. Для существенной
  логики, инварианта или regression добавляй проверку, которая действительно ловит ошибку.

## Уроки, обязательные для соответствующих сценариев

| Слабая проверка | Требуемое доказательство |
| --- | --- |
| Чужой случайный UUID | Другой существующий активный пользователь; отказ при подмене identity/владельца |
| Нового токена нет среди строк БД | Нужный digest существует, связан с правильной сессией, старый использован, новый работает |
| HTTP 204/429 при запросе письма | Помимо статусов — число вызовов SMTP/доставок и адрес получателя |
| Операция успешна, значит атомарна | Сбой после реальной записи до commit; новая session видит полный rollback, повтор допустим |
| Взяли любой пример OpenAPI | Request schema именно проверяемой операции и её пример; подменяются только runtime credentials |
| Два запроса в gather, значит гонка | Синхронизация критических шагов, реальное ожидание/конфликт в БД и оба существенных порядка |

## Структура и инструменты

- pytest, для async — pytest-asyncio с `asyncio_mode = 'auto'`, для HTTP —
  httpx/ASGITransport. Запускай `uv run pytest` в тестовом Docker-контейнере.
- Тесты — модульные функции `test_<action>_<entity>_<condition>`, без test-классов.
  Для async-функции используй `async def`, для чистой sync-логики — обычный `def`.
  В auto-режиме `@pytest.mark.asyncio` не нужен.
- Группируй `tests/<area>/application_test.py`, `gateway_test.py`, `http_test.py`
  или другой единый выбранный стиль. Parametrize имеет понятные IDs.
- Общие engine/client/DI fixtures находятся в `conftest.py`, специфические —
  рядом со сценарием. Не копируй создание приложения и pools в каждый тест.
- Mock-порты создавай через `create_autospec(..., instance=True)`.
  Возвраты, определяющие ветвление, задавай явно: пустой DTO вместо старого None,
  конкретный bool вместо truthy MagicMock. Мокай внешнюю границу, не SQLAlchemy.
- Для read-тестов seed через SQL/model, а не через тот же метод gateway,
  который проверяется. Для write-тестов читай сохранённые данные независимо
  и учитывай устаревшие значения ORM identity map.

## Изоляция БД

- Используй отдельную test-БД того же типа, что в runtime. Не подменяй PostgreSQL
  SQLite ради удобства: семантика транзакций, locks и SQL отличается.
- Test DSN, network и credentials задаются отдельно. Перед drop/create проверяй
  цель; один суффикс `_test` в имени не заменяет изоляцию от рабочей инфраструктуры.
- Для обычных тестов подходит внешняя транзакция с rollback и savepoints для
  внутренних commit. Session-scoped async fixtures и тесты используют согласованный loop.
- Проверка конкуренции и настоящего rollback после commit-границ использует
  независимые request sessions и наблюдателя. Внешняя общая rollback-fixture
  не является доказательством production-транзакций.
- Очистка затрагивает только собственные test rows/schema/volumes и выполняется
  в finally. Настоящие письма и другие внешние эффекты в тестах отключены;
  SMTP проверяется отдельным локальным тестовым сервером.

Пример обычной fixture для SQLAlchemy/PostgreSQL, когда engine уже изолирован:

```python
from collections.abc import AsyncIterator

import pytest
from sqlalchemy.ext.asyncio import AsyncEngine, AsyncSession


@pytest.fixture
async def session(engine: AsyncEngine) -> AsyncIterator[AsyncSession]:
    async with engine.connect() as connection:
        transaction = await connection.begin()
        db_session = AsyncSession(
            bind=connection,
            join_transaction_mode='create_savepoint',
            expire_on_commit=False,
            autoflush=False,
        )
        try:
            yield db_session
        finally:
            await db_session.close()
            await transaction.rollback()
```

## Гонки, UI и ошибки

- Используй Events/барьеры и ограниченное ожидание. Для PostgreSQL при необходимости
  подтверждай блокировку через `pg_blocking_pids` и PID участвующих транзакций.
  `sleep` фиксированной длины и допуск «200 или 401» не обеспечивают нужного порядка.
- После каждого порядка проверяй конечные инварианты: какие credentials работают,
  какие записи/сессии отозваны, нет ли потерянных обновлений.
- Контролируемый сбой вводится после реального изменения состояния; после ошибки
  наблюдатель проверяет rollback, затем проверяется успешный retry/запрет replay.
- Браузерные тесты проверяют пользовательский сценарий с реальным API для важных
  интеграций. Локальный mock времени/ответа подходит для UI-таймера и отдельного 429;
  он не объявляется проверкой SMTP или серверного rate limit.
- Не скрывай гонку retries тестового runner. Сначала устрани причину flaky-теста.
  После исправления повторяй затронутые проверки; полный набор — перед коммитом
  по принятой конфигурации. Пройденный CI не заменяет содержательное ревью.
