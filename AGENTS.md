# Инструкции проекта

Прочитай [.codex/AGENTS.md](.codex/AGENTS.md) и применимые разделы правил до работы.
Требования текущей задачи и явно согласованные решения проекта имеют приоритет
над базовыми предпочтениями этого набора.

- Запускай приложение, БД, миграции и проверки через Docker. Не заменяй
  контейнерный запуск host Python или host PostgreSQL при проблемах с Docker.
- Существующие тесты и фикстуры: импорты можно обновлять; assertions, данные,
  mock-поведение, сценарии, удаление, отключение и переименование тестов требуют
  разрешения пользователя. Одобрение действует на согласованный объём работ;
  повторно его не спрашивай. Новые содержательные тесты разрешены.
- Бизнес-изменения размещай в `application/commands/<area>/`, чтения и атомарные
  прикладные действия — в `application/interactors/<area>/`. Не создавай `use_cases`.
- Application не импортирует infrastructure, включая импорты через совместимые
  модули и реэкспорты. Связывание реализаций находится в composition root.
- Контракты и DTO разделяй по ответственности; импортируй из определяющих модулей.
  Не создавай пустые каталоги, агрегаторы и import-only прослойки ради структуры.
- DB-адаптеры называй gateways. Конкретный gateway напрямую наследует нужные
  узкие Protocol-порты; без промежуточного объединяющего интерфейса и без `@override`.
- Одиночный `get` gateway возвращает существующий DTO с пустыми полями при
  отсутствии записи. Проверяй identity и обязательные поля, а не truthiness объекта.
- Технические auth handlers и выпуск токенов относятся к infrastructure;
  бизнес-авторизация и предметные политики сохраняются в application/domain.
- Каждую существенную проверку связывай с конкретным нарушением, которое она
  должна обнаружить. Не ослабляй тесты для прохождения CI.
- Учитывай Git-правила: проверенные локальные изменения коммить, push выполняй
  только в разрешённом объёме, защищённые ветки не изменяй напрямую.
- Сообщай результат, выполненные проверки и ограничения. Зелёный локальный запуск
  не означает, что удалённый CI уже прошёл; отправка письма не означает его доставку.

## Настройки целевого проекта

- Пакет: `snp_allocation`, Python 3.14, uv; runtime-зависимостей нет.
- Это синхронный CLI и библиотека с чистым вычислительным ядром. Сохраняй
  небольшие модули `allocation`, `diagnostics`, `csv_io` и точку входа;
  отдельные application/domain/ports и DI-контейнер пока не нужны.
- Контракт: строгий приоритет, выравнивание покрытия, партии и детерминированные
  ничьи по `request_id`. Решения и ограничения описаны в `REPORT.md`.
- Сборка проверок: `docker build --target development -t snp-allocation:dev .`.
- Проверки: `docker run --rm snp-allocation:dev uv run --no-sync <command>`,
  где `<command>` — `ruff format --check .`, `ruff check .`, `mypy` и `pytest`.
  Перед коммитом обязательны все четыре проверки.
- Runtime: `docker build --target runtime -t snp-allocation:local .`,
  затем `docker run --rm snp-allocation:local`. БД, миграций, серверных портов
  и Compose-сервисов нет.
- Набор `.codex/python-rules/` подключён из соседнего `codex_rules`.
  Общий источник сохраняется; проектные уточнения находятся в этом файле.
